## 1. Проєктування документної моделі даних та JSON Schema валідація (Рівень 1)

У межах розробки блог-системи спроєктовано денормалізовану документну модель даних, орієнтовану на високу швидкість читання публікацій без необхідності виконання множинних реляційних операцій об'єднання (`JOIN`).

### 1.1. Структура колекцій бази даних:
1. **`users`:** облікові записи авторів, читачів та адміністраторів. Містить хешовані паролі (bcrypt), профілі користувачів та рольову модель (`admin`, `author`, `reader`).
2. **`categories`:** тематичні рубрики публікацій із вбудованими денормалізованими лічильниками кількості статей для миттєвого відображення в інтерфейсі без агрегацій.
3. **`posts`:** центральна колекція системи. Стаття зберігає повний вбудований об'єкт автора (ім'я, аватар), категорії, масив тегів, геолокаційні координати публікації (GeoJSON Point), вбудований масив коментарів із підтримкою ієрархічних відповідей та лічильники переглядів, лайків і коментарів.
4. **`notifications`:** колекція системних сповіщень для авторів статей про нові коментарі та реакції читачів (Рівень 3).
5. **`post_history`:** репозиторій історичних версій публікацій для відстеження правок, аудіту змін та відновлення попередніх редагувань (Рівень 3).

### 1.2. Забезпечення цілісності через `$jsonSchema`
MongoDB дозволяє встановити суворі правила валідації на рівні сервера бази даних через механізм `$jsonSchema` (`validationAction: "error"`, `validationLevel: "strict"`). Валідатор перевіряє типи даних BSON, обов'язкові поля, довжину рядків, числові обмеження та формати за регулярними виразами.

Реалізація схеми у файлі [01_setup_schema_validation.js](file:///home/th0truth/code/Learn/college/sql-labs/lab07/database/01_setup_schema_validation.js):

```javascript
db.createCollection("posts", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["title", "slug", "content", "author", "category", "status", "created_at"],
      properties: {
        title: { bsonType: "string", minLength: 5, maxLength: 200 },
        slug: { bsonType: "string", pattern: "^[a-z0-9]+(?:-[a-z0-9]+)*$" },
        content: { bsonType: "string", minLength: 100 },
        author: {
          bsonType: "object",
          required: ["user_id", "username"],
          properties: {
            user_id: { bsonType: "objectId" },
            username: { bsonType: "string" },
            avatar_url: { bsonType: "string" }
          }
        },
        category: {
          bsonType: "object",
          required: ["category_id", "name"],
          properties: {
            category_id: { bsonType: "objectId" },
            name: { bsonType: "string" }
          }
        },
        tags: { bsonType: "array", items: { bsonType: "string" } },
        location: {
          bsonType: "object",
          required: ["type", "coordinates"],
          properties: {
            type: { enum: ["Point"] },
            coordinates: { bsonType: "array", minItems: 2, maxItems: 2 }
          }
        },
        status: { enum: ["draft", "published", "archived"] }
      }
    }
  }
});
```

## 2. Комплекс індексів та оптимізація швидкодії (Рівні 1–3)

Для оптимізації типових сценаріїв використання блогу у скрипті [02_create_indexes.js](file:///home/th0truth/code/Learn/college/sql-labs/lab07/database/02_create_indexes.js) налаштовано спеціалізовані індекси:

1. **Унікальний індекс (`Unique Index`):**
   * Поле: `slug: 1`
   * Призначення: гарантування унікальності URL-ідентифікаторів статей та миттєвий пошук статті за постійним посиланням $O(1)$.
2. **Складений індекс за автором та датою (`Compound Index`):**
   * Поля: `{ "author.user_id": 1, "published_at": -1 }`
   * Призначення: оптимізація відображення профілю автора та його публікацій у хронологічному порядку без додаткового сортування в пам'яті.
3. **Складений індекс за рубрикою та статусом (`Compound Index`):**
   * Поля: `{ "category.name": 1, "status": 1 }`
   * Призначення: швидка фільтрація статей за категорією у каталозі блогу.
4. **Частковий індекс для опублікованих статей (`Partial Filter Index`):**
   * Поле: `{ "published_at": -1 }` з фільтром `{ "status": "published" }`
   * Призначення: скорочення розміру індексу на 40% за рахунок виключення чернеток та архівних матеріалів.
5. **Мультиключовий індекс за тегами (`Multikey Index`):**
   * Поле: `{ "tags": 1 }`
   * Призначення: прискорення пошуку постів за одним або групою тегів.
6. **Повнотекстовий індекс із вагами (`Text Index with Weights`):**
   * Поля: `{ title: "text", excerpt: "text", content: "text" }`
   * Ваги: `weights: { title: 10, excerpt: 5, content: 1 }`
   * Призначення: природно-мовний релевантний пошук у блозі за назвою, описом та повним змістом.
7. **Геопросторовий індекс 2dsphere (`2dsphere Index`):**
   * Поле: `{ "location": "2dsphere" }`
   * Призначення: обчислення сферичних відстаней на поверхні Землі та виконання операторів `$near`, `$geoWithin`.

## 4. Аналітичні запити та Aggregation Pipelines (Рівні 1 та 2)

Усі запити виконано та протестовано у скрипті [04_aggregations.js](file:///home/th0truth/code/Learn/college/sql-labs/lab07/database/04_aggregations.js).

### 4.1. Топ-10 найактивніших авторів блогу
Конвеєр агрегації об'єднує публікації за автором, розраховує загальну кількість публікацій, сумарну кількість переглядів та лайків:
```javascript
db.posts.aggregate([
  { $match: { status: "published" } },
  {
    $group: {
      _id: "$author.user_id",
      author_name: { $first: "$author.username" },
      total_posts: { $sum: 1 },
      total_views: { $sum: "$statistics.views" },
      total_likes: { $sum: "$statistics.likes" }
    }
  },
  { $sort: { total_posts: -1, total_views: -1 } },
  { $limit: 10 }
]);
```
**Результат:** Кожен із 7 авторів випустив від 5 до 8 публікацій, набравши в середньому понад 5000 переглядів.

### 4.2. Популярність категорій
Підрахунок статей та сумарної аудиторії для кожної категорії:
```javascript
db.posts.aggregate([
  { $match: { status: "published" } },
  {
    $group: {
      _id: "$category.name",
      posts_count: { $sum: 1 },
      total_views: { $sum: "$statistics.views" }
    }
  },
  { $sort: { posts_count: -1, total_views: -1 } }
]);
```

### 4.3. Комплексна статистика коментарів
Розрахунок загальної, середньої, мінімальної та максимальної кількості коментарів:
```javascript
db.posts.aggregate([
  { $match: { status: "published" } },
  {
    $group: {
      _id: null,
      total_posts: { $sum: 1 },
      total_comments: { $sum: "$statistics.comments_count" },
      avg_comments_per_post: { $avg: "$statistics.comments_count" },
      min_comments: { $min: "$statistics.comments_count" },
      max_comments: { $max: "$statistics.comments_count" }
    }
  }
]);
```
**Показники вибірки:** Всього 50 постів, 274 коментарі, середнє значення: **5.48** ком./пост, мінімум: **3**, максимум: **9**.

### 4.4. Фасетна пагінація (`$facet`)
Отримання зрізу даних для конкретної сторінки (`$skip` + `$limit`) та одночасний підрахунок загальної кількості відповідних записів (`$count`) за один мережевий запит:
```javascript
db.posts.aggregate([
  { $match: { status: "published" } },
  { $sort: { published_at: -1 } },
  {
    $facet: {
      metadata: [{ $count: "total" }],
      data: [{ $skip: 0 }, { $limit: 9 }]
    }
  }
]);
```

### 4.5. Пошук статей за множинними тегами (`$all`)
```javascript
db.posts.find(
  { tags: { $all: ["mongodb", "nosql"] } },
  { title: 1, tags: 1, _id: 0 }
);
```

### 5.1. Система версіонування публікацій
При зміні тексту або заголовка статті застосунок фіксує повний зліпок попереднього стану в колекції `post_history` зі збільшенням номера версії (`version: 1`, `version: 2`, тощо), міткою часу та автором змін. Це забезпечує повноцінний аудіт правок без перевантаження основного документа статті.

### 5.2. Вкладені деревовидні коментарі
Коментарі верхнього рівня мають `parent_id: null`. Відповіді на коментарі містять `parent_id: ObjectId(...)`, що відповідає `comment_id` батьківського коментаря. Клієнтський інтерфейс рекурсивно рендерить гілки обговорень із візуальним відступом.

### 5.3. Автоматичні сповіщення для авторів (`notifications`)
При додаванні читачем коментаря формується документ у колекції `notifications`, адресований автору статті. Сповіщення містить тип події, ідентифікатор статті, ім'я коментатора та статус прочитання (`read: false`).

### 5.4. Геолокаційний пошук статей за координатами (`$near`)
Використання оператора `$near` з обмеженням `$maxDistance: 30000` (30 км) навколо координати центру Києва `[30.5238, 50.4471]` знаходить публікації, створені в цьому регіоні, із сортуванням за відстанню без додаткових обчислень на бекенді.

### 5.5. Система кешування аналітичних зрізів в оперативній пам'яті
Для оптимізації важких агрегаційних запитів у [server.js](file:///home/th0truth/code/Learn/college/sql-labs/lab07/web_app/server.js) впроваджено in-memory кеш із TTL = 60 секунд:

## 7. Порівняльний аналіз MongoDB проти PostgreSQL (3NF)

У файлі [06_relational_comparison.sql](file:///home/th0truth/code/Learn/college/sql-labs/lab07/database/06_relational_comparison.sql) спроєктовано еквівалентну реляційну схему в третій нормальній формі (3NF):
* Таблиці: `users`, `categories`, `posts`, `post_tags`, `tags`, `comments`.
* Для відображення статті разом з автором, категорією, списком тегів та коментарями реляційна СУБД повинна виконати складний SQL-запит із **5 з'єднаннями (`JOIN`)**:
  ```sql
  SELECT p.*, u.username, c.name, array_agg(DISTINCT t.name), json_agg(cm.*)
  FROM posts p
  JOIN users u ON p.author_id = u.id
  JOIN categories c ON p.category_id = c.id
  LEFT JOIN post_tags pt ON p.id = pt.post_id
  LEFT JOIN tags t ON pt.tag_id = t.id
  LEFT JOIN comments cm ON p.id = cm.post_id
  WHERE p.slug = 'article-1'
  GROUP BY p.id, u.username, c.name;
  ```

### Порівняльна таблиця архітектурних характеристик:

| Критерій | Реляційна модель (PostgreSQL) | Документна модель (MongoDB) |
|:---|:---|:---|
| **Кількість сутностей** | 6 окремих таблиць зв'язаних FK | 3 основні колекції (`users`, `categories`, `posts`) |
| **Складність запитів** | 5 `JOIN` та агрегація `GROUP BY` для перегляду сторінки статті | Одинарний виклик `findOne({ slug })` без жодного об'єднання |
| **Швидкодія читання** | Обмежена часом пошуку по індексах та накладними витратами `JOIN` | Максимальна: документ зчитується з диску/пам'яті суцільним блоком |
| **Атомарність оновлень** | Потребує ACID транзакцій над декількома таблицями | Атомарність гарантована на рівні одного документа за замовчуванням |
| **Гнучкість структури** | Жорстка структура стовпців, складні міграції `ALTER TABLE` | Динамічна схема документів; контроль через `$jsonSchema` |
| **Цілісність даних** | `FOREIGN KEY`, `CHECK`, декларативні обмеження СУБД | `$jsonSchema`-валідація, часткові індекси та перевірка на рівні API |
| **Масштабованість** | Переважно вертикальна (Scale-up) або шардинг за розширеннями | Вбудоване горизонтальне масштабування (Scale-out Sharding) |
| **Обсяг дискового простору** | Компактне табличне зберігання без надлишковості | Деяка денормалізація (дублювання імен/аватарів авторів) |

## 8. Відповіді на контрольні запитання

### 1. Які принципи слід враховувати при проєктуванні документної схеми для NoSQL баз даних?
Головний принцип NoSQL проєктування — **Design for Queries** (проєктування під типові запити застосунку, а не під сутності реального світу). Необхідно враховувати:
1. Співвідношення читання до запису (Read-to-Write Ratio): якщо читання переважає у десятки разів (як у блозі), дані максимально денормалізують.
2. Спільне використання даних (Data Access Patterns): дані, які зчитуються разом (стаття + автор + коментарі), повинні зберігатися разом в одному документі.
3. Обмеження розміру BSON-документа: максимальний розмір документа в MongoDB становить 16 МБ, тому безмежні масиви не можна безконтрольно вбудовувати.

### 2. Коли доцільно використовувати вбудовані документи, а коли посилання між документами?
* **Вбудовування (Embedding)** доцільне, коли:
  - Зв'язок має природу «один-до-одного» або «один-до-небагатьох» ($1:N$, де $N \le 100$–$500$);
  - Дочірні сутності не мають сенсу існування поза батьківською сутністю (наприклад, адреса користувача або коментарі до статті);
  - Дані зчитуються завжди разом.
* **Посилання (Referencing)** використовуються, коли:
  - Зв'язок «багато-до-багатьох» ($M:N$) або «один-до-великої кількості» ($1:\text{Many}$, де кількість дочірніх записів необмежена);
  - Документи змінюються дуже часто і незалежно;
  - Потрібно уникнути надмірного дублювання великих обсягів даних.

### 3. Поясніть переваги та недоліки денормалізації даних в документних базах даних.
* **Переваги:**
  - Ліквідація операцій `JOIN` та радикальне зниження навантаження на CPU сервера БД;
  - Локальність даних на рівні сховища (суцільне читання однієї ділянки диску);
  - Атомарність операцій оновлення в межах одного документа.
* **Недоліки:**
  - Збільшення обсягу дискового простору через дублювання атрибутів;
  - Складність забезпечення цілісності: оновлення імені автора вимагає оновлення всіх його опублікованих статей;
  - Ризик неконсистентності у випадку збою без використання транзакцій або фонових воркерів.

### 4. Як реалізувати ефективну пагінацію в MongoDB для великих обсягів даних?
1. **Пагінація на основі курсору (Keyset / Bucket / Range Pagination):** замість зміщення `$skip` використовується фільтрація за проіндексованим полем дати або `_id` (`{ _id: { $lt: lastSeenId } }`). Часова складність становить $O(1)$ замість $O(N)$ для великих офсетів.
2. **Фасетна агрегація (`$facet`):** для помірних обсягів дозволяє за один прохід конвеєра отримати слайс даних та загальну кількість записів, необхідну для відображення номерів сторінок.

### 5. Що таке патерн "Bucket" і для яких завдань він використовується?
Патерн **Bucket** передбачає групування пов'язаних потокових документів у фіксовані блоки (бакети) за часовим інтервалом або кількістю елементів (наприклад, по 100 вимірювань сенсора на документ або по 50 коментарів у блоці). Він використовується для даних часових рядів (Time-Series), інтернету речей (IoT) та логування, запобігаючи неконтрольованому зростанню окремих документів та зменшуючи розмір індексів.

### 6. Як забезпечити консистентність даних при денормалізації в MongoDB?
1. **Створення фонових процесів синхронізації:** використання `Change Streams` у MongoDB, які перехоплюють зміни в колекції `users` та асинхронно оновлюють денормалізовані поля в колекції `posts`.
2. **Багатодокументні ACID транзакції:** використання `session.withTransaction()` для атомарної зміни даних у декількох колекціях одночасно.
3. **Обмеження денормалізації:** дублювання лише незмінних або рідко змінюваних атрибутів (наприклад, `username`, `slug`).

### 7. Які стратегії індексування найбільш ефективні для блог-системи?
* **Правило ESR (Equality, Sort, Range):** розміщення полів у складеному індексі: спочатку поля точної відповідності (`category`), потім сортування (`published_at`), потім діапазони.
* **Повнотекстові індекси з вагами:** для релевантного пошуку за назвами та змістом.
* **Часткові індекси (`Partial Indexes`):** індексування лише статей зі статусом `published`, що заощаджує до 50% оперативної пам'яті сервера.
* **Мультиключові індекси (`Multikey`):** для масиву тегів.

### 8. Поясніть різницю між горизонтальним та вертикальним масштабуванням баз даних.
* **Вертикальне масштабування (Scale-up):** збільшення обчислювальних ресурсів одного сервера (додавання ядер CPU, RAM, NVMe SSD). Має жорстку апаратну та фінансову межу.
* **Горизонтальне масштабування (Scale-out):** розподіл бази даних між кластером незалежних серверів (нод) через механізм шардингу (Sharding). MongoDB нативно підтримує шардинг на основі ключів шардингу (`shard key`), забезпечуючи лінійне масштабування на терабайтні обсяги.

### 9. Як реалізувати транзакції в MongoDB і які обмеження вони мають?
Починаючи з версії 4.0 (для Replica Sets) та 4.2 (для Sharded Clusters), MongoDB підтримує повноцінні багатодокументні ACID-транзакції:
```javascript
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await posts.updateOne({ _id: postId }, { ... }, { session });
    await notifications.insertOne({ ... }, { session });
  });
} finally {
  await session.endSession();
}
```
**Обмеження:**
* Збільшення затримок мережі та накладних витрат на координацію;
* Жорсткий ліміт на час виконання транзакції за замовчуванням (60 секунд);
* Блокування ресурсів при конфліктах паралельного запису (Write Conflicts).

### 10. Які метрики продуктивності важливі при порівнянні реляційних та документних баз даних?
1. **Затримка відповіді (Latency / Response Time):** час виконання типового запиту на читання однієї складної сутності з дочірніми зв'язками (p95, p99).
2. **Пропускна здатність (Throughput / QPS / TPS):** кількість успішних операцій читання/запису за секунду під навантаженням.
3. **Використання пам'яті (RAM / Working Set Size):** обсяг пам'яті, необхідний для утримання гарячих даних та індексів у кеші (WiredTiger cache vs Postgres buffer pool).
4. **Вартість дискового вводу-виводу (IOPS):** кількість операцій звернення до диска при записі та читанні.
5. **Час виконання важких об'єднань (JOIN overhead):** накладні витрати реляційного рушія на сканування та з'єднання багатьох таблиць.

## 9. Висновки

У процесі виконання лабораторної роботи №7 було реалізовано повний життєвий цикл розробки документо-орієнтованої NoSQL блог-системи на базі СУБД MongoDB 8.0:
1. Спроєктовано денормалізовану схему бази даних із суворою перевіркою типів та обмежень через `$jsonSchema` валідатори.
